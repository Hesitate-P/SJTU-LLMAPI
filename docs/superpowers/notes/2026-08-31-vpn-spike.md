# VPN Spike 结论（2026-08-31，Task 13）

真实 jAccount 凭据实测 `stu.vpn.sjtu.edu.cn` IKEv2 隧道：**认证、建隧道、数据面、自愈全部打通**。
过程中发现 4 个原实现的真实 bug 与 1 个服务端约束，均已处理（详见"生效配置"与"尝试记录"）。

## 生效配置（最终与原 template/entrypoint 的差异）

### 认证与提案（swanctl.conf.template）
- IKE 提案：`aes256-sha256-modp2048`（列表第一个即中，无需回退）
- ESP 提案：服务端选定 `AES_CBC_128/HMAC_SHA2_256_128`（charon 默认集，未显式配置）
- 认证：服务端 `pubkey`（Let's Encrypt 链，锚点 **ISRG Root X1**，来自系统 CA bundle）；
  客户端 `eap-mschapv2`，`eap_id` = 裸 jAccount 用户名（不带 @sjtu.edu.cn）。
  服务端先发起 **EAP-PEAP**，strongSwan 回 NAK 指明 MSCHAPv2，服务端接受。
- **新增 `vips = 0.0.0.0`**：服务端要求 IKE_AUTH 携带配置载荷请求，否则回 `FAILED_CP_REQUIRED` 且不建 CHILD。
  每次拨号动态分配 VIP（实测池：`111.186.49.x`、`111.186.55.x`，取决于网关节点），并下发 DNS（202.120.2.101 / 202.112.26.40，含纯 IPv6 项）。
- `start_action = start`（原 `none`）：校园网内探测 URL 直连也通（401），失败驱动型重连永远不会触发，必须主动拨号。
- `mobike = no`：非必需（实测 yes/no 数据面表现相同），容器场景固定外层地址，关掉少一个变量。
- **`remote_ts = 0.0.0.0/0`（关键偏离，见下）**。

### 服务端强制全隧道（本 spike 最重要的发现）
协商收窄 TS（`202.120.0.0/16,+IP/32`）**能成功**（服务端还会再做 narrowing），但**数据面被静默丢弃**：
出方向 ESP 计数正常增长，入方向永远 0 字节（tcpdump 证实网关一个 ESP 包都不回；同期 IKE/DPD 双向正常，19ms RTT）。
改成 `0.0.0.0/0` 后数据立即双向打通。结论：学校网关按会话强制全隧道（禁止分流），按协商 TS 标记会话，收窄会话的转发被禁。
且全隧道下**可出公网**（baidu 200、api.deepseek.com 401，均经隧道）。

### 不接管默认路由的实现（对判据 1 意图的替代达成）
判据 1 期望 xfrm 选择器为交大 TS 而非 0/0——服务端约束下无法满足字面要求，改为：
- xfrm policy 确实是 `src=VIP/32 dst=0.0.0.0/0`（见上方原因）；
- 但 `charon.install_routes = no`（真正的关闭方式，见 bug ②），charon 不装任何路由；
- entrypoint 的 `ensure_routes()` 只往 table 220 放 `202.120.0.0/16`（+解析出的 /32），`src=VIP`、经容器网关。
- 效果（实测）：交大目标 → table 220 → src=VIP → 命中 policy → 进隧道；
  其余目标 → main 表 → src=172.21.0.2 → 不命中 policy（src 不匹配）→ 直连。
  `ip route get 110.242.68.66` → `src 172.21.0.2`（不走隧道）；`ip route get 202.120.35.157` → `table 220 src VIP`。
  网关的备用供应商直连不受影响，且 table 220 无默认路由。

## 原实现的 4 个真实 bug（均已修复）

1. **服务器证书校验缺信任锚**：容器没装 `ca-certificates`，且 strongSwan 不读系统信任库，
   且**一个文件只加载一张证书**——`ca-certificates.crt` 整包拷入 x509ca 只会加载不出。
   修复：Dockerfile 装 `ca-certificates` 并用 awk 把 bundle 拆成 150 个单证书文件放入 `/etc/swanctl/x509ca/`。
   （另：校园网内 `deb.debian.org` 实测超时不可用，apt 源改 `mirror.sjtu.edu.cn`，~1MB/s。）
2. **`install_routes = no` 从未生效**：原 entrypoint 往 `strongswan.d/charon/no-routes.conf` 写裸键，
   而该目录被 include 在 `charon.plugins{}` 里 → 变成无效的 `plugins.install_routes` 被静默忽略；
   且 `install_routes` 本就是 **charon 核心选项**（kernel-netlink 读 `charon.install_routes`）。
   修复：`printf 'charon { install_routes = no }' >> /etc/strongswan.conf`（重复段落会合并）。
3. **resolve 插件改坏 resolv.conf**：服务端下发 4 个 DNS（2×IPv4+2×IPv6），插件把容器 resolv.conf
   改到只剩一个**纯 IPv6** 服务器；容器无 IPv6 → 域名解析全挂 → 探测全 000 → 保活循环每 30s 拆建隧道。
   该插件（5.9.8）**没有 resolve=no 开关**（二进制里只有 `file` / `resolvconf.iface_prefix` 两个键），
   修复：`resolve { file = /dev/null }`，容器继续用 Docker 内置 DNS（127.0.0.11 → 宿主解析器）。
4. **docker stop 不发 IKE DELETE → 锁号 4~8 分钟**：学校网关疑似**单会话限制**——旧会话未被 DELETE
   释放时重拨，表现为 MSCHAPv2 内层成功但最终 EAP FAIL，需等网关超时回收（实测 4~8 分钟，期间反复重拨无碍但也无效）。
   修复两处：entrypoint 注册 `trap ... swanctl --terminate --ike sjtu`；且保活循环的 `sleep 30` 改
   `sleep 30 & wait`（前台 sleep 会把 trap 推迟到 sleep 结束，早被 docker 10s 宽限 SIGKILL，trap 根本来不及跑）。

## 尝试记录（时间线）

| 轮次 | 改动 | 结果 |
|---|---|---|
| 1 原版 | — | IKE_SA_INIT OK，`no trusted RSA public key found` → AUTH_FAILED（bug 1） |
| 2 | 装 CA bundle（整包单文件） | 仍不信任（每文件一证书，加载不出） |
| 3 | bundle 拆 150 个文件 | EAP-MSCHAPv2 全通，IKE_SA 建立；CHILD 失败：`FAILED_CP_REQUIRED`+`TS_UNACCEPT` |
| 4 | `vips=0.0.0.0`+`start_action=start` | CHILD 建立 `VIP/32 === 202.120.0.0/16`；但数据面黑洞（出有入无）；期间发现 resolv.conf 被 IPv6 DNS 改坏（bug 3）、保活循环盲区、install_routes 假关闭（bug 2） |
| 5 | `mobike=no` | 数据面仍黑洞 → 排除 MOBIKE 因素 |
| 6 | 临时改 `remote_ts=0.0.0.0/0` | **数据双向打通**（dig 经隧道应答、models 401、baidu 200）→ 锁定服务端全隧道强制 |
| 7 | 定稿：TS 0/0 + `charon.install_routes=no` + `ensure_routes()` 手工 table 220 分流路由 | 分流行为符合设计；models 走隧道（计数 +3140B 入/+1329B 出）、baidu 直连（隧道计数零增长） |
| 8 | trap+wait 修复后 `docker compose restart` | **数秒内** CHILD 重建（EAP/SUCC 即刻），路由刷新到新 VIP，计数恢复增长 |

tcpdump 关键证据（轮次 4-5 期间）：出方向 `UDP-encap ESP(spi=..,seq=1..7)` 每秒一包（DNS/SYN 重传），
入方向 0 包；同期 `inf2[I]→inf2[R]`（DPD）19ms 往返 → 排除 NAT/回程问题，锁定服务端丢弃。
（tcpdump 为临时诊断：从交大镜像拉 deb 解包 docker cp 进容器，未进 Dockerfile。）

## 判据核验（修订版 Step 4）

1. **选择器**：字面不满足——policy 为 `src=VIP/32 dst=0.0.0.0/0`（服务端强制全隧道，见上）；
   "不接管默认路由"的意图由 table 220 分流路由 + src 选择达成，默认出流量实测不走隧道。
2. **bytes 增长**：满足——models 请求前后 in 17841→20981 / out 8821→10150（同 SPI，未重拨）；
   baidu 请求隧道计数零增长（证明分流正确）。
3. **VIP**：分配——每次拨号一个（.143/.148/.55.193），装在 eth0 `/32`，随网关节点走不同池。
4. **install_routes**：不是翻转 yes，而是发现原 no 从未生效；现真正 no + 手工路由，源地址选择实测正确。

自愈验证：`docker compose restart` → 数秒内 CHILD 重建、路由刷新、计数增长（trap 生效，无锁号）。

## 遗留 / 建议（供 Task 14 与后续）

- compose 的 healthcheck 仍是"任意 HTTP 码即健康"，校园网内直连也会 401——与 entrypoint 探测同样的盲区。
  生产上建议 healthcheck 改查 `swanctl --list-sas` 的 INSTALLED（或 xfrm state esp 计数增长）。
- 校外场景 DNS：现在用 Docker 内置 DNS（宿主解析器）。校外若宿主解析不了 `models.sjtu.edu.cn`（校内名），
  需把解析指到 202.120.2.101（该 IP 在 /16 分流路由内，天然走隧道）——Task 14 校外验收时确认。
- 隧道闪断期间（重拨窗口）：交大网段路由仍指向 table 220 但无 policy/state，src=VIP 的包经 docker
  MASQUERADE 后校内仍可达（校园网内可用性不降）；校外则闪断数秒~数分钟，由网关自身故障转移兜底。
- 网关节点轮询（111.186.48.0 / 111.186.54.0）与 VIP 池（49.x / 55.x）的对应关系未深究，不影响功能。
